282  Scoring Models Inside the Database

  • Show All Code
  • Hide All Code
  • View Source

Most tabular models are trained in Python and used somewhere else. The features live in a warehouse, the scores are needed in that same warehouse (for a dashboard, a campaign list, a risk report, or a downstream join), and the usual answer is a pipeline that exports rows, scores them in a Python service, and writes the scores back. That round trip is slow to build, fragile to operate, and a governance headache, because customer data leaves the system whose access controls and audit logs were designed to protect it.

In-database scoring inverts the flow. Instead of moving the data to the model, it moves the model to the data, by expressing the fitted model as something the database can execute natively: a SQL expression, a user-defined function, or a call into a model runtime embedded in the engine. This chapter explains why and when to do it, how a fitted scikit-learn pipeline becomes SQL, how the main deployment options compare, and, most importantly, how to prove that the database computes the same scores as Python. The runnable part builds a pipeline-to-SQL translator by hand, executes the result in SQLite, and tests parity, so that the automatic tools introduced afterward are no longer black boxes.

282.1 Why Score Where the Data Lives

Data gravity. Large tables are expensive to move. Scoring millions of rows in place avoids extraction jobs, network transfer, egress charges, and a second copy of sensitive data in a serving system.

Governance. Inside the warehouse, scoring inherits existing role-based access control, row and column security, lineage, and audit logging. A score computed by a view is versioned with the view definition and can be reproduced for a regulator by rerunning the query against a historical snapshot.

Consistency. When features are defined in SQL and scores are computed in the same query, the model sees exactly the feature values the business sees. A separate Python serving path is a classic source of training-serving skew, where subtly different feature code in two places produces different inputs (Sculley et al. 2015).

Operational simplicity. A scoring view needs no container, no autoscaling, and no on-call rotation beyond the warehouse itself. Batch scoring becomes a scheduled INSERT ... SELECT.

In-database scoring is not free. SQL is a poor language for models with dynamic control flow, large embeddings, or GPU-bound computation, and a warehouse is the wrong place for low-latency online inference behind an API. The database research literature has argued for decades that analytics should run inside the engine, from user-defined aggregates for statistical models (Ordonez 2010) to full in-database machine learning libraries (Hellerstein et al. 2012), and recent systems go further by optimizing data and model operators together in one query plan (Karanasos et al. 2020, Park et al. 2022).

282.2 The Options

There are four broad ways to run a trained model inside a database.

  1. Compile the model to plain SQL. Linear models become arithmetic expressions, one-hot encoders and trees become CASE WHEN expressions, and ensembles become sums of trees. The result runs on any engine with no extra runtime, uses the engine’s optimizer and parallelism, and is fully transparent. The Posit orbital library automates this for scikit-learn pipelines, using ONNX as an intermediate representation and emitting SQL for many dialects through the sqlglot library.
  2. Run Python inside the database as a user-defined function (UDF). Snowflake (Snowpark Python UDFs and vectorized UDFs), BigQuery (remote functions), Databricks, and PostgreSQL (PL/Python) can execute Python next to the data. This supports any model, at the price of a Python sandbox, package management, and per-batch serialization overhead.
  3. Call a native model runtime. Several engines can load a serialized model, often in ONNX format, and evaluate it with an embedded runtime. BigQuery ML can import ONNX and other external models for ML.PREDICT, and research prototypes such as Raven integrate ONNX Runtime directly into the query processor of SQL Server (Karanasos et al. 2020). Compilers such as Hummingbird translate traditional models into tensor programs that such runtimes, and GPUs, execute efficiently (Nakandala et al. 2020).
  4. Train in the database. BigQuery ML, Snowflake ML functions, and MADlib on PostgreSQL train and score with SQL syntax. This avoids translation entirely but restricts you to the algorithms and preprocessing the platform provides.

For the models that dominate tabular production work (regularized linear and logistic regression, single trees, and tree ensembles of moderate size), option 1 is often the best default, and it is the one this chapter builds from first principles.

282.3 From Pipeline to SQL: The Math

Consider a typical scikit-learn pipeline for a binary outcome: numeric features are median-imputed and standardized, categorical features are one-hot encoded with unknown categories ignored, and a logistic regression produces a probability. For numeric feature \(j\) with training median \(\tilde{x}_j\), mean \(\mu_j\), and scale \(\sigma_j\), and categorical feature \(k\) with levels \(\mathcal{C}_k\), the linear predictor is \[ \eta(\mathbf{x}) = b + \sum_{j} w_j \,\frac{\operatorname{impute}(x_j) - \mu_j}{\sigma_j} + \sum_{k}\sum_{c \in \mathcal{C}_k} v_{k,c}\, \mathbb{1}[x_k = c], \qquad p(\mathbf{x}) = \frac{1}{1 + e^{-\eta(\mathbf{x})}} . \] Each piece has a direct SQL counterpart. Imputation is COALESCE(x, median). Standardization is arithmetic. The indicator sum for one categorical feature is a single CASE x WHEN 'a' THEN v_a WHEN 'b' THEN v_b ELSE 0 END, where the ELSE 0 branch reproduces handle_unknown="ignore", since an unseen category activates no column. The constants can be folded, which shortens the SQL: \[ \eta(\mathbf{x}) = \underbrace{b - \sum_j \frac{w_j \mu_j}{\sigma_j}}_{b'} + \sum_j \frac{w_j}{\sigma_j}\operatorname{impute}(x_j) + \sum_k \sum_c v_{k,c}\,\mathbb{1}[x_k = c] . \] A decision tree is a nested conditional. Each internal node tests \(x_f \le t\) and each leaf returns a class probability, so the tree becomes nested CASE WHEN x_f <= t THEN ... ELSE ... END. A gradient-boosted ensemble with \(M\) trees and learning rate folded into the leaves is \(\eta(\mathbf{x}) = b + \sum_{m=1}^{M} \text{tree}_m(\mathbf{x})\), a sum of \(M\) such expressions. The SQL grows with the total number of leaves, which is why tools offer options such as emitting each tree as a separate subexpression.

How much numerical error is acceptable? SQL and NumPy both use IEEE double precision, but they add terms in different orders, and a translator must print every constant as decimal text. Floating-point addition is not associative, so differences at the level of machine epsilon are expected and harmless (Goldberg 1991). Printing constants with too few digits is not harmless. If the literal for \(w_j\) is off by \(\delta_j\), the linear predictor moves by \(\sum_j \delta_j x_j\), and since \(\mathrm{d}p/\mathrm{d}\eta = p(1-p) \le \tfrac14\), \[ |\Delta p| \le \tfrac14\, |\Delta \eta| \le \tfrac14 \sum_j |\delta_j|\,|x_j| . \] Printing every float with Python’s repr produces the shortest decimal string that round-trips to the identical double, which removes this error source entirely.

282.4 Building the Translator

We start with a synthetic customer churn table with numeric and categorical features and some missing values, and fit the pipeline described above.

train, test = train_test_split(df, test_size=0.25, random_state=0, stratify=df["churn"])

pipe = Pipeline([

        ("cat", OneHotEncoder(handle_unknown="ignore"), cat_cols),

]).fit(train[num_cols + cat_cols], train["churn"])

print(f"train rows {len(train)}, test rows {len(test)}, churn rate {df['churn'].mean():.3f}")
print(f"test accuracy {pipe.score(test[num_cols + cat_cols], test['churn']):.3f}")

The translator reads the fitted parameters out of each step and writes the folded expression. It handles exactly the steps in this pipeline and refuses anything else, which is the right behavior for a hand-written translator: silently mistranslating an unsupported step is far worse than failing loudly.

Code 
def lit(x: float, digits: int | None = None) -> str:
    """SQL literal for a float. repr() round-trips exactly. `digits` rounds on purpose."""
    return repr(float(x)) if digits is None else f"{float(x):.{digits}g}"


def quote(s: str) -> str:
    return "'" + str(s).replace("'", "''") + "'"


def logistic_pipeline_to_sql(pipe, table, id_col, digits=None, impute=True):
    prep, clf = pipe.named_steps["prep"], pipe.named_steps["clf"]
    coef, intercept = clf.coef_.ravel(), float(clf.intercept_[0])
    terms, pos = [], 0
    for name, trans, cols in prep.transformers_:
        if name == "remainder":
            continue
        if name == "num":
            imp, sc = trans.named_steps["impute"], trans.named_steps["scale"]
            assert isinstance(imp, SimpleImputer) and isinstance(sc, StandardScaler)
            for j, col in enumerate(cols):
                w = coef[pos + j] / sc.scale_[j]
                intercept -= w * sc.mean_[j]
                x = f"COALESCE({col}, {lit(imp.statistics_[j], digits)})" if impute else col
                terms.append(f"{lit(w, digits)} * {x}")
            pos += len(cols)
        elif name == "cat":
            assert isinstance(trans, OneHotEncoder) and trans.handle_unknown == "ignore"
            for col, cats in zip(cols, trans.categories_):
                whens = " ".join(f"WHEN {quote(c)} THEN {lit(coef[pos + i], digits)}"
                                 for i, c in enumerate(cats))
                terms.append(f"(CASE {col} {whens} ELSE 0.0 END)")
                pos += len(cats)
        else:
            raise NotImplementedError(f"cannot translate transformer {name!r}")
    assert pos == len(coef), "every coefficient must be consumed exactly once"
    logit = f"{lit(intercept, digits)}\n    + " + "\n    + ".join(terms)
    return (f"SELECT {id_col},\n       logit,\n       1.0 / (1.0 + exp(-logit)) AS p_churn\n"
            f"FROM (SELECT {id_col},\n    {logit} AS logit\n  FROM {table})")


sql = logistic_pipeline_to_sql(pipe, "customers", "customer_id")
print(sql)

282.5 Testing Parity

A translated model is only trustworthy if it is tested against the original on the same rows. We load the test set into an in-memory SQLite database, run the query, and compare against predict_proba and decision_function row by row. SQLite stands in for the warehouse here. 282.5.2 Trees and a subtle float32 trap

A decision tree translates into nested CASE expressions. The same parity test applies, with one twist worth knowing about: scikit-learn’s tree estimators convert their input to 32-bit floats before comparing it with the (64-bit) thresholds, while SQL compares in 64-bit arithmetic. Values extremely close to a threshold can therefore be routed differently.

282.7 Pitfalls and When to Use

Test parity, always, and on purpose-built edge cases. Compare Python and SQL scores row by row on a fixed sample that includes missing values, unseen categories, boundary values, and extreme values. Fail the build on any NULL score, on probability differences above a tolerance near machine precision for SQL-compiled linear models, or on any change in predicted label beyond a small allowance for tree models evaluated in 32-bit arithmetic.

Missing values are the most common bug. SQL NULL propagates through arithmetic and fails every comparison, so x <= t is neither true nor false for a missing x. Make every imputation explicit with COALESCE, and decide deliberately which branch a missing value takes in a tree.

Categories must match exactly. String comparison in SQL is sensitive to case, whitespace, and collation settings, which may differ from Python. Normalize categorical values with the same function on both sides, and test that a category that looks the same in a dashboard actually matches.

Print constants exactly. Use round-trip float formatting. Rounded literals are a silent source of error that grows with feature magnitude.

Mind numerical limits of the engine. Clip logits before exp, watch integer division in engines where 1/2 is zero, and check decimal types, since some warehouses default numeric literals to fixed-point decimals with limited scale.

Version the SQL with the model. The generated view is the deployed model. Store it in version control next to the training code and the parity test, and record the model version as a column in the scored output, so that every score can be traced to the exact model that produced it.

Know when not to do it. Deep networks, large embeddings, text models, and low-latency online scoring belong in a model server or a dedicated runtime. In-database scoring shines for batch and near-real-time scoring of tabular models over data that already lives in the warehouse, which describes a large share of production machine learning in practice.

# Scoring Models Inside the Database {#sec-in-database-scoring}

Most tabular models are trained in Python and used somewhere else. The features live in a warehouse, the scores are needed in that same warehouse (for a dashboard, a campaign list, a risk report, or a downstream join), and the usual answer is a pipeline that exports rows, scores them in a Python service, and writes the scores back. That round trip is slow to build, fragile to operate, and a governance headache, because customer data leaves the system whose access controls and audit logs were designed to protect it.

**In-database scoring** inverts the flow. Instead of moving the data to the model, it moves the model to the data, by expressing the fitted model as something the database can execute natively: a SQL expression, a user-defined function, or a call into a model runtime embedded in the engine. This chapter explains why and when to do it, how a fitted scikit-learn pipeline becomes SQL, how the main deployment options compare, and, most importantly, how to *prove* that the database computes the same scores as Python. The runnable part builds a pipeline-to-SQL translator by hand, executes the result in SQLite, and tests parity, so that the automatic tools introduced afterward are no longer black boxes.

## Why Score Where the Data Lives

**Data gravity.** Large tables are expensive to move. Scoring millions of rows in place avoids extraction jobs, network transfer, egress charges, and a second copy of sensitive data in a serving system.

**Governance.** Inside the warehouse, scoring inherits existing role-based access control, row and column security, lineage, and audit logging. A score computed by a view is versioned with the view definition and can be reproduced for a regulator by rerunning the query against a historical snapshot.

**Consistency.** When features are defined in SQL and scores are computed in the same query, the model sees exactly the feature values the business sees. A separate Python serving path is a classic source of **training-serving skew**, where subtly different feature code in two places produces different inputs (Sculley et al. 2015).

**Operational simplicity.** A scoring view needs no container, no autoscaling, and no on-call rotation beyond the warehouse itself. Batch scoring becomes a scheduled `INSERT ... SELECT`.

In-database scoring is not free. SQL is a poor language for models with dynamic control flow, large embeddings, or GPU-bound computation, and a warehouse is the wrong place for low-latency online inference behind an API. The database research literature has argued for decades that analytics should run inside the engine, from user-defined aggregates for statistical models (Ordonez 2010) to full in-database machine learning libraries (Hellerstein et al. 2012), and recent systems go further by optimizing data and model operators together in one query plan (Karanasos et al. 2020, Park et al. 2022).

## The Options

There are four broad ways to run a trained model inside a database.

1. **Compile the model to plain SQL.** Linear models become arithmetic expressions, one-hot encoders and trees become `CASE WHEN` expressions, and ensembles become sums of trees. The result runs on any engine with no extra runtime, uses the engine's optimizer and parallelism, and is fully transparent. The Posit `orbital` library automates this for scikit-learn pipelines, using ONNX as an intermediate representation and emitting SQL for many dialects through the sqlglot library.
2. **Run Python inside the database as a user-defined function (UDF).** Snowflake (Snowpark Python UDFs and vectorized UDFs), BigQuery (remote functions), Databricks, and PostgreSQL (PL/Python) can execute Python next to the data. This supports any model, at the price of a Python sandbox, package management, and per-batch serialization overhead.
3. **Call a native model runtime.** Several engines can load a serialized model, often in ONNX format, and evaluate it with an embedded runtime. BigQuery ML can import ONNX and other external models for `ML.PREDICT`, and research prototypes such as Raven integrate ONNX Runtime directly into the query processor of SQL Server (Karanasos et al. 2020). Compilers such as Hummingbird translate traditional models into tensor programs that such runtimes, and GPUs, execute efficiently (Nakandala et al. 2020).
4. **Train in the database.** BigQuery ML, Snowflake ML functions, and MADlib on PostgreSQL train and score with SQL syntax. This avoids translation entirely but restricts you to the algorithms and preprocessing the platform provides.

For the models that dominate tabular production work (regularized linear and logistic regression, single trees, and tree ensembles of moderate size), option 1 is often the best default, and it is the one this chapter builds from first principles.

## From Pipeline to SQL: The Math

Consider a typical scikit-learn pipeline for a binary outcome: numeric features are median-imputed and standardized, categorical features are one-hot encoded with unknown categories ignored, and a logistic regression produces a probability. For numeric feature $j$ with training median $\tilde{x}_j$, mean $\mu_j$, and scale $\sigma_j$, and categorical feature $k$ with levels $\mathcal{C}_k$, the linear predictor is
$$
\eta(\mathbf{x}) = b + \sum_{j} w_j \,\frac{\operatorname{impute}(x_j) - \mu_j}{\sigma_j} + \sum_{k}\sum_{c \in \mathcal{C}_k} v_{k,c}\, \mathbb{1}[x_k = c],
\qquad
p(\mathbf{x}) = \frac{1}{1 + e^{-\eta(\mathbf{x})}} .
$$
Each piece has a direct SQL counterpart. Imputation is `COALESCE(x, median)`. Standardization is arithmetic. The indicator sum for one categorical feature is a single `CASE x WHEN 'a' THEN v_a WHEN 'b' THEN v_b ELSE 0 END`, where the `ELSE 0` branch reproduces `handle_unknown="ignore"`, since an unseen category activates no column. The constants can be folded, which shortens the SQL:
$$
\eta(\mathbf{x}) = \underbrace{b - \sum_j \frac{w_j \mu_j}{\sigma_j}}_{b'} + \sum_j \frac{w_j}{\sigma_j}\operatorname{impute}(x_j) + \sum_k \sum_c v_{k,c}\,\mathbb{1}[x_k = c] .
$$
A decision tree is a nested conditional. Each internal node tests $x_f \le t$ and each leaf returns a class probability, so the tree becomes nested `CASE WHEN x_f <= t THEN ... ELSE ... END`. A gradient-boosted ensemble with $M$ trees and learning rate folded into the leaves is $\eta(\mathbf{x}) = b + \sum_{m=1}^{M} \text{tree}_m(\mathbf{x})$, a sum of $M$ such expressions. The SQL grows with the total number of leaves, which is why tools offer options such as emitting each tree as a separate subexpression.

**How much numerical error is acceptable?** SQL and NumPy both use IEEE double precision, but they add terms in different orders, and a translator must print every constant as decimal text. Floating-point addition is not associative, so differences at the level of machine epsilon are expected and harmless (Goldberg 1991). Printing constants with too few digits is not harmless. If the literal for $w_j$ is off by $\delta_j$, the linear predictor moves by $\sum_j \delta_j x_j$, and since $\mathrm{d}p/\mathrm{d}\eta = p(1-p) \le \tfrac14$,
$$
|\Delta p| \le \tfrac14\, |\Delta \eta| \le \tfrac14 \sum_j |\delta_j|\,|x_j| .
$$
Printing every float with Python's `repr` produces the shortest decimal string that round-trips to the identical double, which removes this error source entirely.

                   "total_charges": total, "contract": contract, "payment_method": payment,
                   "internet_service": internet, "churn": churn})
num_cols = ["tenure", "monthly_charges", "total_charges"]
cat_cols = ["contract", "payment_method", "internet_service"]
train, test = train_test_split(df, test_size=0.25, random_state=0, stratify=df["churn"])

pipe = Pipeline([
    ("prep", ColumnTransformer([
        ("num", Pipeline([("impute", SimpleImputer(strategy="median")),
                          ("scale", StandardScaler())]), num_cols),
        ("cat", OneHotEncoder(handle_unknown="ignore"), cat_cols),
    ])),
    ("clf", LogisticRegression(max_iter=2000)),
]).fit(train[num_cols + cat_cols], train["churn"])

print(f"train rows {len(train)}, test rows {len(test)}, churn rate {df['churn'].mean():.3f}")
print(f"test accuracy {pipe.score(test[num_cols + cat_cols], test['churn']):.3f}")
```

The translator reads the fitted parameters out of each step and writes the folded expression. It handles exactly the steps in this pipeline and refuses anything else, which is the right behavior for a hand-written translator: silently mistranslating an unsupported step is far worse than failing loudly.

```{python}
#| label: code-1210-translate
def lit(x: float, digits: int | None = None) -> str:
    """SQL literal for a float. repr() round-trips exactly. `digits` rounds on purpose."""
    return repr(float(x)) if digits is None else f"{float(x):.{digits}g}"


def quote(s: str) -> str:
    return "'" + str(s).replace("'", "''") + "'"


def logistic_pipeline_to_sql(pipe, table, id_col, digits=None, impute=True):
    prep, clf = pipe.named_steps["prep"], pipe.named_steps["clf"]
    coef, intercept = clf.coef_.ravel(), float(clf.intercept_[0])
    terms, pos = [], 0
    for name, trans, cols in prep.transformers_:
        if name == "remainder":
            continue
        if name == "num":
            imp, sc = trans.named_steps["impute"], trans.named_steps["scale"]
            assert isinstance(imp, SimpleImputer) and isinstance(sc, StandardScaler)
            for j, col in enumerate(cols):
                w = coef[pos + j] / sc.scale_[j]
                intercept -= w * sc.mean_[j]
                x = f"COALESCE({col}, {lit(imp.statistics_[j], digits)})" if impute else col
                terms.append(f"{lit(w, digits)} * {x}")
            pos += len(cols)
        elif name == "cat":
            assert isinstance(trans, OneHotEncoder) and trans.handle_unknown == "ignore"
            for col, cats in zip(cols, trans.categories_):
                whens = " ".join(f"WHEN {quote(c)} THEN {lit(coef[pos + i], digits)}"
                                 for i, c in enumerate(cats))
                terms.append(f"(CASE {col} {whens} ELSE 0.0 END)")
                pos += len(cats)
        else:
            raise NotImplementedError(f"cannot translate transformer {name!r}")
    assert pos == len(coef), "every coefficient must be consumed exactly once"
    logit = f"{lit(intercept, digits)}\n    + " + "\n    + ".join(terms)
    return (f"SELECT {id_col},\n       logit,\n       1.0 / (1.0 + exp(-logit)) AS p_churn\n"
            f"FROM (SELECT {id_col},\n    {logit} AS logit\n  FROM {table})")


sql = logistic_pipeline_to_sql(pipe, "customers", "customer_id")
print(sql)
```

The output is a single readable query. Every number in it is a fitted parameter, and every line corresponds to one feature, so a reviewer who knows SQL but not scikit-learn can audit what the model does.

## Testing Parity

A translated model is only trustworthy if it is tested against the original on the same rows. We load the test set into an in-memory SQLite database, run the query, and compare against `predict_proba` and `decision_function` row by row. SQLite stands in for the warehouse here. The test logic is identical against Snowflake, BigQuery, or PostgreSQL.

```{python}
#| label: code-1210-parity
con = sqlite3.connect(":memory:")
try:
    con.execute("SELECT exp(1.0)").fetchone()
except sqlite3.OperationalError:                 # SQLite built without math functions
    import math
    con.create_function("exp", 1, math.exp, deterministic=True)

test[["customer_id"] + num_cols + cat_cols].to_sql("customers", con, index=False)


def score_sql(query):
    out = pd.read_sql_query(query, con).set_index("customer_id")
    return out.loc[test["customer_id"]]


def parity_report(sql_scores, label):
    X = test[num_cols + cat_cols]
    p_py = pipe.predict_proba(X)[:, 1]
    eta_py = pipe.decision_function(X)
    p_sql = sql_scores["p_churn"].to_numpy(dtype=float)
    ok = ~np.isnan(p_sql)                        # compare only rows that received a score
    return {"translation": label,
            "null scores": int((~ok).sum()),
            "max |logit diff|": np.abs(sql_scores["logit"].to_numpy(dtype=float)[ok] - eta_py[ok]).max(),
            "max |p diff|": np.abs(p_sql[ok] - p_py[ok]).max(),
            "label flips at 0.5": int(((p_sql[ok] >= 0.5) != (p_py[ok] >= 0.5)).sum())}


t0 = time.perf_counter()
exact = score_sql(sql)
elapsed = time.perf_counter() - t0
reports = [parity_report(exact, "exact literals")]
naive = score_sql(logistic_pipeline_to_sql(pipe, "customers", "customer_id", impute=False))
reports.append(parity_report(naive, "no COALESCE"))
print(pd.DataFrame(reports).set_index("translation"))
print(f"\nscored {len(exact)} rows in SQLite in {elapsed * 1000:.1f} ms")
```

The exact translation agrees with Python to within floating-point rounding on every row. The naive translation, which omits the `COALESCE` that implements the imputer, returns `NULL` for every row with a missing value, because SQL arithmetic propagates `NULL`. This is the most common real-world translation bug, and it is silent: the query succeeds, the scores for complete rows are perfect, and the missing scores show up weeks later as customers who were never contacted.

Edge cases deserve their own tests, because the test split may not contain them. Below we score rows with an unseen payment method, a missing value, and extreme numeric values.

```{python}
#| label: code-1210-edge-cases
edge = pd.DataFrame({
    "customer_id": [900001, 900002, 900003, 900004],
    "tenure": [0.0, 72.0, np.nan, 1e6],
    "monthly_charges": [18.0, 120.0, 55.5, 1e6],
    "total_charges": [np.nan, 9000.0, np.nan, 1e9],
    "contract": ["month-to-month", "two-year", "one-year", "month-to-month"],
    "payment_method": ["crypto", "card", "cash", "card"],          # "crypto" never seen in training
    "internet_service": ["fiber", "none", "dsl", "fiber"],
})
edge.to_sql("edge", con, index=False)
e_sql = pd.read_sql_query(logistic_pipeline_to_sql(pipe, "edge", "customer_id"), con)
e_py = pipe.predict_proba(edge[num_cols + cat_cols])[:, 1]
print(pd.DataFrame({"customer_id": edge["customer_id"], "p_python": e_py,
                    "p_sql": e_sql["p_churn"], "abs diff": np.abs(e_py - e_sql["p_churn"])}))
```

Unseen categories contribute zero in both systems, missing values are imputed identically, and extreme inputs saturate the sigmoid in both. Saturation is benign for SQLite's `exp`, but some engines raise an overflow error for `exp` of a large positive number, so production SQL often clips the logit to a range such as $[-30, 30]$ before exponentiating.

### Literal precision

The next experiment isolates the error from printing constants with too few significant digits, which is what a hand-written translation or a careless code generator does.

```{python}
#| label: fig-1210-precision
#| fig-cap: "Absolute difference between Python and SQL churn probabilities on the test set when model constants are printed with 3, 6, or 9 significant digits, or with exact round-trip literals. Rounded literals introduce errors many orders of magnitude above floating-point rounding."
p_py = pipe.predict_proba(test[num_cols + cat_cols])[:, 1]
diffs, rows = {}, []
for digits in [3, 6, 9, None]:
    label = "exact (repr)" if digits is None else f"{digits} significant digits"
    s = score_sql(logistic_pipeline_to_sql(pipe, "customers", "customer_id", digits=digits))
    d = np.abs(s["p_churn"].to_numpy(dtype=float) - p_py)
    diffs[label] = np.maximum(d, 1e-18)                       # floor so exact zeros plot on log axis
    rows.append({"literals": label, "max |p diff|": d.max(), "median |p diff|": np.median(d),
                 "label flips at 0.5": int(((s["p_churn"].to_numpy() >= 0.5) != (p_py >= 0.5)).sum())})
print(pd.DataFrame(rows).set_index("literals"))

fig, ax = plt.subplots(figsize=(8, 4))
bins = np.logspace(-18, -1, 60)
for label, d in diffs.items():
    ax.hist(d, bins=bins, histtype="step", linewidth=1.8, label=label)
ax.set_xscale("log")
ax.set_xlabel("|p_SQL - p_Python| (values below 1e-17 shown at the floor)")
ax.set_ylabel("test rows")
ax.legend()
fig.tight_layout()
plt.show()
```

Each added digit shrinks the error by roughly the expected factor, yet every rounded variant stays far above the rounding floor. Whether a given error flips a decision depends on how many customers sit that close to a threshold. On a test set of this size it may be none, but across millions of scored customers some always will, and rankings used for targeting shift as well. Exact literals leave only the unavoidable rounding from a different summation order. The lesson is to generate SQL programmatically with exact literals and to set the parity tolerance close to machine precision, so that any real translation error stands out.

### Trees and a subtle float32 trap

A decision tree translates into nested `CASE` expressions. The same parity test applies, with one twist worth knowing about: scikit-learn's tree estimators convert their input to 32-bit floats before comparing it with the (64-bit) thresholds, while SQL compares in 64-bit arithmetic. Values extremely close to a threshold can therefore be routed differently.

```{python}
#| label: code-1210-tree
tree_pipe = Pipeline([
    ("prep", ColumnTransformer([
        ("num", SimpleImputer(strategy="median"), num_cols),
        ("cat", OneHotEncoder(handle_unknown="ignore"), cat_cols),
    ])),
    ("tree", DecisionTreeClassifier(max_depth=4, min_samples_leaf=50, random_state=0)),
]).fit(train[num_cols + cat_cols], train["churn"])

prep_t = tree_pipe.named_steps["prep"]
feature_sql = [f"COALESCE({c}, {lit(m)})"
               for c, m in zip(num_cols, prep_t.named_transformers_["num"].statistics_)]
for col, cats in zip(cat_cols, prep_t.named_transformers_["cat"].categories_):
    feature_sql += [f"(CASE WHEN {col} = {quote(c)} THEN 1.0 ELSE 0.0 END)" for c in cats]

t = tree_pipe.named_steps["tree"].tree_


def node_sql(i, indent=2):
    pad = " " * indent
    if t.children_left[i] == -1:                              # leaf: class-1 probability
        v = t.value[i, 0]
        return lit(v[1] / v.sum())
    return (f"CASE WHEN {feature_sql[t.feature[i]]} <= {lit(t.threshold[i])}\n"
            f"{pad}THEN {node_sql(t.children_left[i], indent + 2)}\n"
            f"{pad}ELSE {node_sql(t.children_right[i], indent + 2)} END")


tree_sql = f"SELECT customer_id, {node_sql(0)} AS p_churn FROM customers"
s_tree = pd.read_sql_query(tree_sql, con).set_index("customer_id").loc[test["customer_id"]]
p_tree = tree_pipe.predict_proba(test[num_cols + cat_cols])[:, 1]
print(f"tree leaves: {t.n_leaves}, SQL length: {len(tree_sql)} characters")
print(f"max |p diff| on the test set: {np.abs(s_tree['p_churn'].to_numpy() - p_tree).max():.2e}")

# Probe every numeric threshold with the smallest double just above it.
probes = 0
for i in np.where(t.children_left != -1)[0]:
    f = t.feature[i]
    if f >= len(num_cols):
        continue                                              # one-hot splits are 0/1 only
    x_above = np.nextafter(t.threshold[i], np.inf)
    sklearn_goes_left = np.float32(x_above) <= t.threshold[i]
    probes += int(sklearn_goes_left)                          # SQL always goes right here
n_numeric = int(sum(t.feature[i] < len(num_cols) for i in np.where(t.children_left != -1)[0]))
print(f"numeric thresholds where a value just above the threshold is routed "
      f"differently by scikit-learn and SQL: {probes} of {n_numeric}")
```

On real data the tree scores agree exactly, because observed values almost never land within a 32-bit rounding step of a threshold. The probe shows that for a fraction of thresholds a disagreeing input *exists*: a value a hair above the threshold, which SQL sends right and scikit-learn, after rounding to 32 bits, sends left. ONNX-based tools typically compute in 32-bit floats as well, so the same caution applies to them, and practitioners have reported rare prediction differences of exactly this kind. The defensible approach is a parity test with a small tolerance on probabilities plus a monitored count of label disagreements, not an assumption of bitwise equality.

## Automating the Translation

Writing translators by hand is instructive but does not scale to many model types. The `orbital` library converts a fitted scikit-learn pipeline into SQL automatically. It parses the pipeline (internally via ONNX) given the column types, and exports SQL for a chosen dialect. The chunk below shows the workflow against Snowflake with Snowpark. It requires the packages and a Snowflake account, so it is not executed here.

```{python}

    "account": os.environ["SNOWFLAKE_ACCOUNT"],
    "user": os.environ["SNOWFLAKE_USER"],

Not every transformer and model can be represented as SQL, so pin the library version, check the supported list for that version, and keep the parity test running in CI.

## Pitfalls and When to Use

**Test parity, always, and on purpose-built edge cases.** Compare Python and SQL scores row by row on a fixed sample that includes missing values, unseen categories, boundary values, and extreme values. Fail the build on any `NULL` score, on probability differences above a tolerance near machine precision for SQL-compiled linear models, or on any change in predicted label beyond a small allowance for tree models evaluated in 32-bit arithmetic.

**Missing values are the most common bug.** SQL `NULL` propagates through arithmetic and fails every comparison, so `x <= t` is neither true nor false for a missing `x`. Make every imputation explicit with `COALESCE`, and decide deliberately which branch a missing value takes in a tree.

**Categories must match exactly.** String comparison in SQL is sensitive to case, whitespace, and collation settings, which may differ from Python. Normalize categorical values with the same function on both sides, and test that a category that looks the same in a dashboard actually matches.

**Print constants exactly.** Use round-trip float formatting. Rounded literals are a silent source of error that grows with feature magnitude.

**Mind numerical limits of the engine.** Clip logits before `exp`, watch integer division in engines where `1/2` is zero, and check decimal types, since some warehouses default numeric literals to fixed-point decimals with limited scale.

**Version the SQL with the model.** The generated view is the deployed model. Store it in version control next to the training code and the parity test, and record the model version as a column in the scored output, so that every score can be traced to the exact model that produced it.

**Know when not to do it.** Deep networks, large embeddings, text models, and low-latency online scoring belong in a model server or a dedicated runtime. In-database scoring shines for batch and near-real-time scoring of tabular models over data that already lives in the warehouse, which describes a large share of production machine learning in practice.
