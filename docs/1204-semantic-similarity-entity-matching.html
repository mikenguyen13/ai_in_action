230  Semantic Text Similarity and Entity Matching

  • Show All Code
  • Hide All Code
  • View Source

Two strings can mean the same thing while sharing almost no characters (“JPMorgan Chase & Co” and “JPM”), and two strings can share almost every character while meaning different things (“bán” means to sell in Vietnamese and “bàn” means table). Every system that deduplicates customers, links a news article to a company, matches a supplier invoice to a vendor master, or ranks web pages against an industry description has to decide, pair by pair, how similar two pieces of text are and whether that similarity is strong enough to act on.

This chapter treats the problem as a ladder. The bottom rung is lexical similarity: edit distance, set overlap, and TF-IDF cosine over words or character n-grams. These methods are cheap, transparent, and surprisingly strong for names. The middle rung is embedding similarity, where a neural encoder maps text to vectors so that paraphrases land close together. Sentence embeddings themselves are developed in Chapter 228 and Chapter 229, so here we focus on how to use them for matching, in particular the split between bi-encoders and cross-encoders. The top rung is entity matching (also called record linkage or entity resolution), where several fields are compared at once and a probabilistic model decides which record pairs refer to the same real-world entity. Throughout, we keep a multilingual lens and use Vietnamese as the running example, because its diacritics and multi-syllable words break naive pipelines in instructive ways.

230.1 Lexical Similarity

230.1.1 Edit distance

The Levenshtein distance \(d(a, b)\) between strings \(a\) and \(b\) is the minimum number of single-character insertions, deletions, and substitutions that turn \(a\) into \(b\) (Levenshtein 1966). It is computed by dynamic programming over a table \(D\) whose entry \(D_{i,j}\) is the distance between the first \(i\) characters of \(a\) and the first \(j\) characters of \(b\): \[ D_{i,j} = \min\big( D_{i-1,j} + 1,\ D_{i,j-1} + 1,\ D_{i-1,j-1} + \mathbb{1}[a_i \neq b_j] \big), \qquad D_{i,0} = i,\ D_{0,j} = j . \] The cost is \(O(|a|\,|b|)\) time. To compare strings of different lengths we normalize to a similarity in \([0, 1]\): \[ \text{sim}_{\text{lev}}(a, b) = 1 - \frac{d(a, b)}{\max(|a|, |b|)} . \] The Damerau variant also counts a transposition of adjacent characters as one edit, which matters for typed data where “Nugyen” for “Nguyen” is common (Damerau 1964). For short person names the Jaro-Winkler similarity, designed at the US Census Bureau for exactly this setting, rewards agreement at the start of the string, where typing errors are rarer (Winkler 1990). Navarro (2001) surveys the algorithmic side of approximate string matching.

Edit distance is sensitive to word order. “Chase JPMorgan” and “JPMorgan Chase” are far apart in Levenshtein terms even though a human sees the same name. A cheap fix is token sort: lowercase, split into tokens, sort them alphabetically, rejoin, and only then compute the edit distance.

230.1.2 Set overlap and character n-grams

The Jaccard similarity of two sets is the size of their intersection over the size of their union (Jaccard 1912): \[ J(A, B) = \frac{|A \cap B|}{|A \cup B|} . \] Applied to word sets it ignores order entirely. Applied to the set of character \(n\)-grams of a padded string (for \(n = 3\), “data” becomes ” da”, “dat”, “ata”, “ta”) it tolerates typos, since one wrong character destroys at most \(n\) of the \(n\)-grams and leaves the rest intact. Character n-grams also absorb morphology: “business” and “businesses” share most of their trigrams while being different word tokens.

230.1.3 TF-IDF cosine

Set overlap treats every token as equally informative. In a list of company names, the token “inc” carries almost no evidence while “netflix” carries a great deal. TF-IDF weighting captures this (Salton and Buckley 1988). For a term \(t\) in document \(d\) drawn from a collection of \(N\) documents, \[ w_{t,d} = \text{tf}(t, d) \cdot \log\frac{1 + N}{1 + \text{df}(t)} + \text{tf}(t, d), \] where \(\text{df}(t)\) is the number of documents containing \(t\) (this is the smoothed form used by scikit-learn, which adds one to the logarithm). Each document becomes a vector \(\mathbf{w}_d\), normalized to unit length, and similarity is the cosine \[ \cos(\mathbf{w}_a, \mathbf{w}_b) = \frac{\mathbf{w}_a^\top \mathbf{w}_b}{\lVert \mathbf{w}_a\rVert\,\lVert \mathbf{w}_b \rVert} . \] The “terms” can be words or character n-grams. TF-IDF over character n-grams within word boundaries is the workhorse of industrial company-name matching: it is a sparse matrix product, it scales to millions of names with approximate nearest-neighbor search over sparse vectors, and it inherits both the typo tolerance of n-grams and the down-weighting of boilerplate such as legal suffixes.

230.1.4 Comparing the lexical measures

The example below compares the measures on a small task: score three website snippets against a short industry description, as one would when classifying firms by the text on their websites. Everything is implemented from scratch except the TF-IDF vectorizer.

def levenshtein(a: str, b: str) -> int:
    """Edit distance by the two-row dynamic program."""
    if len(a) < len(b):
        a, b = b, a
    prev = list(range(len(b) + 1))
    for i, ca in enumerate(a, 1):
        cur = [i]
        for j, cb in enumerate(b, 1):
            cur.append(min(prev[j] + 1, cur[j - 1] + 1, prev[j - 1] + (ca != cb)))
        prev = cur
    return prev[-1]


def lev_sim(a: str, b: str) -> float:
    if not a and not b:
        return 1.0
    return 1.0 - levenshtein(a, b) / max(len(a), len(b))


def char_ngrams(s: str, n: int = 3) -> set:
    s = f" {s} "
    return {s[i:i + n] for i in range(len(s) - n + 1)}


def jaccard(A: set, B: set) -> float:
    return len(A & B) / len(A | B) if (A | B) else 1.0


def tfidf_cos(query, docs, **kw):
    vec = TfidfVectorizer(**kw).fit([query] + docs)
    return cosine_similarity(vec.transform([query]), vec.transform(docs))[0]

The measures disagree, and the disagreement is informative. Whole-string Levenshtein mostly reflects length and shared function words, so it is a poor choice for comparing sentences. Word-level TF-IDF with English stop words removed sees only exact token matches: “business” in the first snippet and “businesses” in the description are different tokens, so the first snippet gets credit only for “data”. The character n-gram variant links “business” and “businesses” through their shared n-grams. None of these methods knows that a “data seller” is closer to a “data warehouse” business than a physical “warehouse” is. That gap is what embeddings close, and we return to it below.

230.2 Multilingual Text: The Vietnamese Case

Lexical methods silently assume that equal-looking text is equal at the byte level and that whitespace separates words. Vietnamese violates both assumptions, and so do many other languages, so it is worth working through the details.

Diacritics and Unicode normalization. Vietnamese uses the Latin alphabet with a rich set of diacritics: vowel modifiers (ă, â, ê, ô, ơ, ư), the letter đ, and five tone marks. A character such as “ữ” can be stored as a single precomposed code point (Unicode Normalization Form C, NFC) or as a base letter followed by combining marks (Form D, NFD). The two encodings render identically and compare unequal. Text pasted from different keyboards, operating systems, and PDF extractors arrives in a mixture of both. Worse, many users type Vietnamese without any diacritics at all, so “dữ liệu” (data) also appears as “du lieu”.

Syllables versus words. Vietnamese writes one syllable per whitespace-delimited token, and most words are compounds of two or more syllables: “dữ liệu” (data), “công nghệ” (technology), “buôn bán” (trade). Splitting on whitespace therefore produces syllables, and a syllable such as “liệu” carries little meaning alone. Word segmenters such as VnCoreNLP (Vu et al. 2018) and the underthesea toolkit join syllables into words (“dữ_liệu”), and the Vietnamese language model PhoBERT expects word-segmented input (Nguyen and Nguyen 2020).

The next chunk demonstrates both problems and the standard fixes: NFC normalization, optional diacritic folding, syllable bigrams as a cheap stand-in for word segmentation, and character n-grams.

Code 
def nfc(s: str) -> str:
    return unicodedata.normalize("NFC", s)


def fold_vi(s: str) -> str:
    """Strip Vietnamese diacritics: decompose, drop combining marks, map đ to d."""
    s = unicodedata.normalize("NFD", s)
    s = "".join(ch for ch in s if unicodedata.category(ch) != "Mn")
    return s.replace("đ", "d").replace("Đ", "D")


word = "dữ liệu"
w_nfc, w_nfd = nfc(word), unicodedata.normalize("NFD", word)
print("renders the same:", w_nfc, "|", w_nfd)
print("equal as strings:", w_nfc == w_nfd, "| code points:", len(w_nfc), "vs", len(w_nfd))

# The default TF-IDF token pattern treats combining marks as non-word characters,

analyzer = TfidfVectorizer().build_analyzer()

The NFD form is not merely different from the NFC form, it is tokenized into different pieces, so any similarity computed on mixed-normalization text is corrupted at the first step. The fix is mechanical: normalize every string to NFC at ingestion, before storage, hashing, or indexing.

Diacritic folding is a judgment call. It makes “du lieu” match “dữ liệu”, which is usually what a search box or a name matcher wants. It also merges sell, table, friend, copy, and busy into a single token, which destroys meaning for semantic tasks. A robust pattern is to index both forms and let the folded form contribute recall while the accented form contributes precision.

230.3 Embedding Similarity: Bi-Encoders and Cross-Encoders

Lexical methods cannot know that “nhà cung cấp công nghệ” and “technology vendor” mean the same thing. Neural encoders can. Two architectures dominate.

A bi-encoder maps each text independently to a vector \(f_\theta(x) \in \mathbb{R}^k\) and scores a pair by cosine similarity, \[ s_{\text{bi}}(q, d) = \cos\big(f_\theta(q), f_\theta(d)\big). \] Because documents are encoded once and stored, scoring a query against \(N\) documents costs one encoder pass plus a nearest-neighbor search. Sentence-BERT made this practical by fine-tuning BERT in a siamese configuration so that cosine similarity of pooled outputs is meaningful (Reimers and Gurevych 2019). Multilingual bi-encoders such as LaBSE (Feng et al. 2022) and BGE-M3 (Chen et al. 2024) place translations near each other, so a Vietnamese query can retrieve an English document.

A cross-encoder feeds the pair through the transformer jointly and outputs a score, \[ s_{\text{cross}}(q, d) = g_\phi\big([\texttt{CLS}]\ q\ [\texttt{SEP}]\ d\big), \] so every token of \(q\) attends to every token of \(d\). Cross-encoders are more accurate on fine-grained distinctions (negation, swapped roles, numbers) but cost one full forward pass per pair, so they cannot search a large collection directly (Humeau et al. 2020). The standard production design is retrieve then rerank: a bi-encoder (often combined with a sparse lexical retriever such as BM25 or the char-gram TF-IDF above) retrieves the top \(k\) candidates, and a cross-encoder reorders only those \(k\).

Two practical warnings carry over from Chapter 228. First, a raw pretrained encoder that was never trained for similarity, such as the [CLS] vector of PhoBERT, gives poorly calibrated cosines, so use a model fine-tuned for sentence similarity or fine-tune one on in-domain pairs. Second, cosine scores are not probabilities and their scale differs across models, so thresholds must be chosen on labeled pairs for each model. The Massive Text Embedding Benchmark compares models across tasks and languages and is a sensible place to shortlist candidates, but it does not replace an in-domain evaluation (Muennighoff et al. 2023).

230.5 Entity Matching and Record Linkage

Real records have several fields, and no single field is decisive. Two customer records with the same family name “Nguyễn” are weak evidence of a match, because a very large share of Vietnamese people carry that name. The same birth year and province are stronger evidence, and a rare given name stronger still. Record linkage formalizes how to combine such evidence. The classic reference is Christen (2012).

230.5.1 The Fellegi-Sunter model

Consider two files \(A\) and \(B\) and the set of all pairs \((a, b) \in A \times B\). Each pair is either a match (\(M\)) or a non-match (\(U\)). For each of \(K\) fields we compute a comparison outcome \(\gamma_k \in \{0, 1\}\) (agree or disagree, possibly after fuzzy comparison), giving a vector \(\boldsymbol{\gamma} = (\gamma_1, \dots, \gamma_K)\). Fellegi and Sunter (1969) define the m-probabilities and u-probabilities \[ m_k = P(\gamma_k = 1 \mid M), \qquad u_k = P(\gamma_k = 1 \mid U). \] The \(m_k\) measure field reliability (how often true matches agree, which typos and data entry errors push below one). The \(u_k\) measure coincidental agreement (how often unrelated records agree, which is large for “Nguyễn” and small for a rare given name). Under conditional independence of fields given match status, the log-likelihood ratio of a comparison vector is a sum of per-field match weights: \[ W(\boldsymbol{\gamma}) = \sum_{k=1}^{K} \left[\gamma_k \log_2 \frac{m_k}{u_k} + (1 - \gamma_k) \log_2 \frac{1 - m_k}{1 - u_k}\right]. \] Agreement on a field adds a positive weight and disagreement subtracts. Fellegi and Sunter showed that the optimal decision rule, for given tolerated rates of false matches and false non-matches, uses two thresholds: declare a match when \(W > T_\mu\), a non-match when \(W < T_\lambda\), and send the pairs in between to clerical review.

The \(m_k\) and \(u_k\) are usually unknown. Because the comparison vectors come from a two-component mixture, they can be estimated without labels by the EM algorithm. With mixing proportion \(p = P(M)\) and the conditional independence assumption, the E-step computes for each pair \[ g(\boldsymbol{\gamma}) = \frac{p \prod_k m_k^{\gamma_k}(1 - m_k)^{1 - \gamma_k}}{p \prod_k m_k^{\gamma_k}(1 - m_k)^{1 - \gamma_k} + (1 - p) \prod_k u_k^{\gamma_k}(1 - u_k)^{1 - \gamma_k}}, \] and the M-step updates \(p\), \(m_k\), and \(u_k\) as \(g\)-weighted and \((1-g)\)-weighted agreement rates. Since only \(2^K\) distinct comparison vectors exist, EM runs on pattern counts and is instantaneous even for millions of pairs.

230.5.2 Blocking

Comparing all \(|A| \cdot |B|\) pairs is quadratic and wasteful, since almost all pairs are non-matches. Blocking compares only pairs that share a blocking key (Papadakis et al. 2020). Two metrics describe a blocking scheme. The reduction ratio is the fraction of the full comparison space that is skipped, and the pairs completeness is the fraction of true matches that survive blocking: \[ \text{RR} = 1 - \frac{|C|}{|A| \cdot |B|}, \qquad \text{PC} = \frac{|C \cap M|}{|M|}, \] where \(C\) is the set of candidate pairs. A match lost at blocking can never be recovered downstream, so PC is a hard ceiling on recall. Using a union of several blocking keys protects against errors in any one field.

Every candidate pair was admitted because it agrees on birth year or on the start of the given name, so among candidates coincidental agreement on those two fields is common and their \(u\) values are inflated. Weights estimated after blocking are conditional on the blocking design and must be re-estimated whenever the keys change. Second, EM pushes \(m\) for day and month close to one, slightly above the oracle values. The few true matches whose day and month were swapped look, to the model, like non-matches, so the model learns that real matches essentially never disagree on those fields and then penalizes those pairs heavily. This is the conditional independence assumption failing in a specific, recognizable way: a swap makes two fields disagree together.

230.5.4 Choosing thresholds and evaluating

230.6 Beyond the Classical Pipeline

The modern stack keeps the same skeleton (normalize, block, compare, decide) and upgrades individual stages. Deep entity matchers such as Ditto serialize each record into text and fine-tune a pretrained transformer as a cross-encoder over record pairs, with large gains on dirty and textual records (Li et al. 2020). Since 2023, generative LLMs have been used as zero-shot or few-shot matchers that read two serialized records and answer whether they match, and published comparisons show they can rival fine-tuned matchers on unseen entity types, at a much higher cost per pair (Peeters et al. 2025). Because cost per pair is the binding constraint, these models belong at the end of the pipeline: lexical or embedding blocking reduces the space, Fellegi-Sunter or a small classifier settles the clear cases, and the LLM or a human reviews the narrow ambiguous band.

230.7 Pitfalls and When to Use What

Normalize Unicode before anything else. Mixed NFC and NFD text corrupts tokens, hashes, and joins silently. Normalize to NFC at ingestion. Decide separately, per task, whether to fold diacritics, and when in doubt index both forms.

Do not fold diacritics for semantic tasks. Folding is a recall tool for names and search. For meaning, it merges distinct Vietnamese words and hurts any downstream model trained on accented text.

Treat syllable tokenization as a known approximation. Whitespace splits Vietnamese into syllables. Use a word segmenter, syllable bigrams, or character n-grams, and feed word-segmented text to models such as PhoBERT that expect it.

Thresholds are model specific. A cosine of 0.8 means different things for TF-IDF, for one embedding model, and for another. Calibrate thresholds on labeled pairs from your own data, and recalibrate when you change the model.

Blocking caps recall. Measure pairs completeness on a labeled sample before tuning the matcher. Use a union of keys on independent fields and avoid keys whose values are highly concentrated, such as Vietnamese family names.

The conditional independence assumption is wrong but useful. Fields such as province and phone area code are correlated, which makes Fellegi-Sunter overconfident. The ranking of pairs usually survives, but posterior probabilities should be recalibrated on labeled data before they are reported as probabilities.

Pairwise decisions must be reconciled. If \(a\) matches \(b\) and \(b\) matches \(c\), but \(a\) does not match \(c\), the pairwise output is inconsistent. Resolve it with a one-to-one assignment when each file has unique entities, or with clustering of the match graph for deduplication, and evaluate at the cluster level as well as the pair level.

Pick the cheapest method that works. For short names, normalized character n-gram TF-IDF is fast, transparent, and hard to beat. For sentences and cross-lingual text, use a fine-tuned bi-encoder for retrieval and a cross-encoder or LLM to rerank. For multi-field records, use blocking plus Fellegi-Sunter or a supervised classifier, and spend expensive models only on the ambiguous band.

# Semantic Text Similarity and Entity Matching {#sec-semantic-similarity-entity-matching}

Two strings can mean the same thing while sharing almost no characters ("JPMorgan Chase & Co" and "JPM"), and two strings can share almost every character while meaning different things ("bán" means *to sell* in Vietnamese and "bàn" means *table*). Every system that deduplicates customers, links a news article to a company, matches a supplier invoice to a vendor master, or ranks web pages against an industry description has to decide, pair by pair, how similar two pieces of text are and whether that similarity is strong enough to act on.

This chapter treats the problem as a ladder. The bottom rung is **lexical similarity**: edit distance, set overlap, and TF-IDF cosine over words or character n-grams. These methods are cheap, transparent, and surprisingly strong for names. The middle rung is **embedding similarity**, where a neural encoder maps text to vectors so that paraphrases land close together. Sentence embeddings themselves are developed in @sec-sentence-embeddings and @sec-sbert, so here we focus on how to *use* them for matching, in particular the split between bi-encoders and cross-encoders. The top rung is **entity matching** (also called record linkage or entity resolution), where several fields are compared at once and a probabilistic model decides which record pairs refer to the same real-world entity. Throughout, we keep a multilingual lens and use Vietnamese as the running example, because its diacritics and multi-syllable words break naive pipelines in instructive ways.

## Lexical Similarity

### Edit distance

The **Levenshtein distance** $d(a, b)$ between strings $a$ and $b$ is the minimum number of single-character insertions, deletions, and substitutions that turn $a$ into $b$ (Levenshtein 1966). It is computed by dynamic programming over a table $D$ whose entry $D_{i,j}$ is the distance between the first $i$ characters of $a$ and the first $j$ characters of $b$:
$$
D_{i,j} = \min\big( D_{i-1,j} + 1,\ D_{i,j-1} + 1,\ D_{i-1,j-1} + \mathbb{1}[a_i \neq b_j] \big),
\qquad D_{i,0} = i,\ D_{0,j} = j .
$$
The cost is $O(|a|\,|b|)$ time. To compare strings of different lengths we normalize to a similarity in $[0, 1]$:
$$
\text{sim}_{\text{lev}}(a, b) = 1 - \frac{d(a, b)}{\max(|a|, |b|)} .
$$
The Damerau variant also counts a transposition of adjacent characters as one edit, which matters for typed data where "Nugyen" for "Nguyen" is common (Damerau 1964). For short person names the **Jaro-Winkler** similarity, designed at the US Census Bureau for exactly this setting, rewards agreement at the start of the string, where typing errors are rarer (Winkler 1990). Navarro (2001) surveys the algorithmic side of approximate string matching.

Edit distance is sensitive to word order. "Chase JPMorgan" and "JPMorgan Chase" are far apart in Levenshtein terms even though a human sees the same name. A cheap fix is **token sort**: lowercase, split into tokens, sort them alphabetically, rejoin, and only then compute the edit distance.

### Set overlap and character n-grams

The **Jaccard similarity** of two sets is the size of their intersection over the size of their union (Jaccard 1912):
$$
J(A, B) = \frac{|A \cap B|}{|A \cup B|} .
$$
Applied to word sets it ignores order entirely. Applied to the set of character $n$-grams of a padded string (for $n = 3$, "data" becomes " da", "dat", "ata", "ta ") it tolerates typos, since one wrong character destroys at most $n$ of the $n$-grams and leaves the rest intact. Character n-grams also absorb morphology: "business" and "businesses" share most of their trigrams while being different word tokens.

### TF-IDF cosine

Set overlap treats every token as equally informative. In a list of company names, the token "inc" carries almost no evidence while "netflix" carries a great deal. **TF-IDF** weighting captures this (Salton and Buckley 1988). For a term $t$ in document $d$ drawn from a collection of $N$ documents,
$$
w_{t,d} = \text{tf}(t, d) \cdot \log\frac{1 + N}{1 + \text{df}(t)} + \text{tf}(t, d),
$$
where $\text{df}(t)$ is the number of documents containing $t$ (this is the smoothed form used by scikit-learn, which adds one to the logarithm). Each document becomes a vector $\mathbf{w}_d$, normalized to unit length, and similarity is the cosine
$$
\cos(\mathbf{w}_a, \mathbf{w}_b) = \frac{\mathbf{w}_a^\top \mathbf{w}_b}{\lVert \mathbf{w}_a\rVert\,\lVert \mathbf{w}_b \rVert} .
$$
The "terms" can be words or character n-grams. TF-IDF over character n-grams within word boundaries is the workhorse of industrial company-name matching: it is a sparse matrix product, it scales to millions of names with approximate nearest-neighbor search over sparse vectors, and it inherits both the typo tolerance of n-grams and the down-weighting of boilerplate such as legal suffixes.

### Comparing the lexical measures

The example below compares the measures on a small task: score three website snippets against a short industry description, as one would when classifying firms by the text on their websites. Everything is implemented from scratch except the TF-IDF vectorizer.

```{python}
def levenshtein(a: str, b: str) -> int:
    """Edit distance by the two-row dynamic program."""
    if len(a) < len(b):
        a, b = b, a
    prev = list(range(len(b) + 1))
    for i, ca in enumerate(a, 1):
        cur = [i]
        for j, cb in enumerate(b, 1):
            cur.append(min(prev[j] + 1, cur[j - 1] + 1, prev[j - 1] + (ca != cb)))
        prev = cur
    return prev[-1]


def lev_sim(a: str, b: str) -> float:
    if not a and not b:
        return 1.0
    return 1.0 - levenshtein(a, b) / max(len(a), len(b))


def char_ngrams(s: str, n: int = 3) -> set:
    s = f" {s} "
    return {s[i:i + n] for i in range(len(s) - n + 1)}


def jaccard(A: set, B: set) -> float:
    return len(A & B) / len(A | B) if (A | B) else 1.0


def tfidf_cos(query, docs, **kw):
    vec = TfidfVectorizer(**kw).fit([query] + docs)
    return cosine_similarity(vec.transform([query]), vec.transform(docs))[0]


industry = "industry data warehouse and data for businesses"
websites = [
    "We are the best business data seller in the country",
    "We can give you the best warehouse for you in the country",
    "Look no further for your warehouse needs",
]

q = industry.lower()
rows = []
for i, w in enumerate(websites):
    d = w.lower()
    rows.append({
        "site": f"site {i + 1}",
        "levenshtein": lev_sim(q, d),
        "jaccard_words": jaccard(set(q.split()), set(d.split())),
        "jaccard_char3": jaccard(char_ngrams(q), char_ngrams(d)),

lex = pd.DataFrame(rows).set_index("site")
lex["tfidf_words"] = tfidf_cos(industry, websites, stop_words="english")
lex["tfidf_char_wb"] = tfidf_cos(industry, websites, analyzer="char_wb", ngram_range=(2, 4))
print(lex.round(3))
print("\nbest site per measure:")
print(lex.idxmax())
```

The measures disagree, and the disagreement is informative. Whole-string Levenshtein mostly reflects length and shared function words, so it is a poor choice for comparing sentences. Word-level TF-IDF with English stop words removed sees only exact token matches: "business" in the first snippet and "businesses" in the description are different tokens, so the first snippet gets credit only for "data". The character n-gram variant links "business" and "businesses" through their shared n-grams. None of these methods knows that a "data seller" is closer to a "data warehouse" business than a physical "warehouse" is. That gap is what embeddings close, and we return to it below.

## Multilingual Text: The Vietnamese Case

Lexical methods silently assume that equal-looking text is equal at the byte level and that whitespace separates words. Vietnamese violates both assumptions, and so do many other languages, so it is worth working through the details.

**Diacritics and Unicode normalization.** Vietnamese uses the Latin alphabet with a rich set of diacritics: vowel modifiers (ă, â, ê, ô, ơ, ư), the letter đ, and five tone marks. A character such as "ữ" can be stored as a single precomposed code point (Unicode Normalization Form C, NFC) or as a base letter followed by combining marks (Form D, NFD). The two encodings render identically and compare unequal. Text pasted from different keyboards, operating systems, and PDF extractors arrives in a mixture of both. Worse, many users type Vietnamese without any diacritics at all, so "dữ liệu" (data) also appears as "du lieu".

**Syllables versus words.** Vietnamese writes one *syllable* per whitespace-delimited token, and most words are compounds of two or more syllables: "dữ liệu" (data), "công nghệ" (technology), "buôn bán" (trade). Splitting on whitespace therefore produces syllables, and a syllable such as "liệu" carries little meaning alone. Word segmenters such as VnCoreNLP (Vu et al. 2018) and the underthesea toolkit join syllables into words ("dữ_liệu"), and the Vietnamese language model PhoBERT expects word-segmented input (Nguyen and Nguyen 2020).

The next chunk demonstrates both problems and the standard fixes: NFC normalization, optional diacritic folding, syllable bigrams as a cheap stand-in for word segmentation, and character n-grams.

```{python}
#| label: code-1204-vietnamese-normalization
def nfc(s: str) -> str:
    return unicodedata.normalize("NFC", s)


def fold_vi(s: str) -> str:
    """Strip Vietnamese diacritics: decompose, drop combining marks, map đ to d."""
    s = unicodedata.normalize("NFD", s)
    s = "".join(ch for ch in s if unicodedata.category(ch) != "Mn")
    return s.replace("đ", "d").replace("Đ", "D")


word = "dữ liệu"
w_nfc, w_nfd = nfc(word), unicodedata.normalize("NFD", word)
print("renders the same:", w_nfc, "|", w_nfd)
print("equal as strings:", w_nfc == w_nfd, "| code points:", len(w_nfc), "vs", len(w_nfd))

# The default TF-IDF token pattern treats combining marks as non-word characters,
# so NFD text is shredded into fragments before any similarity is computed.
analyzer = TfidfVectorizer().build_analyzer()
print("NFC tokens:", analyzer(w_nfc))
print("NFD tokens:", analyzer(w_nfd))
print("folded    :", fold_vi(word))

# Folding is lossy: distinct words collapse onto one form.
syllables = ["bán", "bàn", "bạn", "bản", "ban", "bận"]
print("folding collisions:", {s: fold_vi(s) for s in syllables})
```

The NFD form is not merely different from the NFC form, it is tokenized into different pieces, so any similarity computed on mixed-normalization text is corrupted at the first step. The fix is mechanical: normalize every string to NFC at ingestion, before storage, hashing, or indexing.

Diacritic folding is a judgment call. It makes "du lieu" match "dữ liệu", which is usually what a search box or a name matcher wants. It also merges *sell*, *table*, *friend*, *copy*, and *busy* into a single token, which destroys meaning for semantic tasks. A robust pattern is to index both forms and let the folded form contribute recall while the accented form contributes precision.

## Embedding Similarity: Bi-Encoders and Cross-Encoders

Lexical methods cannot know that "nhà cung cấp công nghệ" and "technology vendor" mean the same thing. Neural encoders can. Two architectures dominate.

A **bi-encoder** maps each text independently to a vector $f_\theta(x) \in \mathbb{R}^k$ and scores a pair by cosine similarity,
$$
s_{\text{bi}}(q, d) = \cos\big(f_\theta(q), f_\theta(d)\big).
$$
Because documents are encoded once and stored, scoring a query against $N$ documents costs one encoder pass plus a nearest-neighbor search. Sentence-BERT made this practical by fine-tuning BERT in a siamese configuration so that cosine similarity of pooled outputs is meaningful (Reimers and Gurevych 2019). Multilingual bi-encoders such as LaBSE (Feng et al. 2022) and BGE-M3 (Chen et al. 2024) place translations near each other, so a Vietnamese query can retrieve an English document.

A **cross-encoder** feeds the pair through the transformer jointly and outputs a score,
$$
s_{\text{cross}}(q, d) = g_\phi\big([\texttt{CLS}]\ q\ [\texttt{SEP}]\ d\big),
$$
so every token of $q$ attends to every token of $d$. Cross-encoders are more accurate on fine-grained distinctions (negation, swapped roles, numbers) but cost one full forward pass *per pair*, so they cannot search a large collection directly (Humeau et al. 2020). The standard production design is **retrieve then rerank**: a bi-encoder (often combined with a sparse lexical retriever such as BM25 or the char-gram TF-IDF above) retrieves the top $k$ candidates, and a cross-encoder reorders only those $k$.

Two practical warnings carry over from @sec-sentence-embeddings. First, a raw pretrained encoder that was never trained for similarity, such as the `[CLS]` vector of PhoBERT, gives poorly calibrated cosines, so use a model fine-tuned for sentence similarity or fine-tune one on in-domain pairs. Second, cosine scores are not probabilities and their scale differs across models, so thresholds must be chosen on labeled pairs for each model. The Massive Text Embedding Benchmark compares models across tasks and languages and is a sensible place to shortlist candidates, but it does not replace an in-domain evaluation (Muennighoff et al. 2023).

The code below shows the retrieve-then-rerank pattern with current multilingual models. It downloads several gigabytes of weights, so it is not executed in this book.

## Name Matching

Company and person names are short, so the semantic machinery of embeddings adds less than it does for sentences, while the specific noise of names (typos, abbreviations, legal suffixes, reordered tokens, dropped diacritics) is exactly what lexical methods handle well. ## Entity Matching and Record Linkage

Real records have several fields, and no single field is decisive. Two customer records with the same family name "Nguyễn" are weak evidence of a match, because a very large share of Vietnamese people carry that name. The same birth year and province are stronger evidence, and a rare given name stronger still. **Record linkage** formalizes how to combine such evidence. The classic reference is Christen (2012).

### The Fellegi-Sunter model

Consider two files $A$ and $B$ and the set of all pairs $(a, b) \in A \times B$. Each pair is either a match ($M$) or a non-match ($U$). For each of $K$ fields we compute a comparison outcome $\gamma_k \in \{0, 1\}$ (agree or disagree, possibly after fuzzy comparison), giving a vector $\boldsymbol{\gamma} = (\gamma_1, \dots, \gamma_K)$. Fellegi and Sunter (1969) define the **m-probabilities** and **u-probabilities**
$$
m_k = P(\gamma_k = 1 \mid M), \qquad u_k = P(\gamma_k = 1 \mid U).
$$
The $m_k$ measure field reliability (how often true matches agree, which typos and data entry errors push below one). The $u_k$ measure coincidental agreement (how often unrelated records agree, which is large for "Nguyễn" and small for a rare given name). Under conditional independence of fields given match status, the log-likelihood ratio of a comparison vector is a sum of per-field **match weights**:
$$
W(\boldsymbol{\gamma}) = \sum_{k=1}^{K} \left[\gamma_k \log_2 \frac{m_k}{u_k} + (1 - \gamma_k) \log_2 \frac{1 - m_k}{1 - u_k}\right].
$$
Agreement on a field adds a positive weight and disagreement subtracts. Fellegi and Sunter showed that the optimal decision rule, for given tolerated rates of false matches and false non-matches, uses two thresholds: declare a match when $W > T_\mu$, a non-match when $W < T_\lambda$, and send the pairs in between to clerical review.

The $m_k$ and $u_k$ are usually unknown. Because the comparison vectors come from a two-component mixture, they can be estimated without labels by the EM algorithm. With mixing proportion $p = P(M)$ and the conditional independence assumption, the E-step computes for each pair
$$
g(\boldsymbol{\gamma}) = \frac{p \prod_k m_k^{\gamma_k}(1 - m_k)^{1 - \gamma_k}}{p \prod_k m_k^{\gamma_k}(1 - m_k)^{1 - \gamma_k} + (1 - p) \prod_k u_k^{\gamma_k}(1 - u_k)^{1 - \gamma_k}},
$$
and the M-step updates $p$, $m_k$, and $u_k$ as $g$-weighted and $(1-g)$-weighted agreement rates. Since only $2^K$ distinct comparison vectors exist, EM runs on pattern counts and is instantaneous even for millions of pairs.

### Blocking

Comparing all $|A| \cdot |B|$ pairs is quadratic and wasteful, since almost all pairs are non-matches. **Blocking** compares only pairs that share a blocking key (Papadakis et al. 2020). Two metrics describe a blocking scheme. The **reduction ratio** is the fraction of the full comparison space that is skipped, and the **pairs completeness** is the fraction of true matches that survive blocking:
$$
\text{RR} = 1 - \frac{|C|}{|A| \cdot |B|}, \qquad \text{PC} = \frac{|C \cap M|}{|M|},
$$
where $C$ is the set of candidate pairs. A match lost at blocking can never be recovered downstream, so PC is a hard ceiling on recall. Using a union of several blocking keys protects against errors in any one field.

Next, the comparison vectors and the EM fit of the Fellegi-Sunter model. Given names are compared with normalized Levenshtein similarity at a threshold, so a single typo still counts as agreement.

```{python}

a_idx, b_idx = cand[:, 0], cand[:, 1]

def giv_agree(x, y, thr=0.75):
    key = (x, y)
    if key not in _lev_cache:
        _lev_cache[key] = lev_sim(x, y) >= thr
    return _lev_cache[key]

G = np.column_stack([
    A["fam_f"].to_numpy()[a_idx] == B["fam_f"].to_numpy()[b_idx],
    (A["mid_f"].to_numpy()[a_idx] == B["mid_f"].to_numpy()[b_idx]),
    [giv_agree(x, y) for x, y in zip(A["giv_f"].to_numpy()[a_idx], B["giv_f"].to_numpy()[b_idx])],
    A["year"].to_numpy()[a_idx] == B["year"].to_numpy()[b_idx],
    A["month"].to_numpy()[a_idx] == B["month"].to_numpy()[b_idx],
    A["day"].to_numpy()[a_idx] == B["day"].to_numpy()[b_idx],
    A["prov_f"].to_numpy()[a_idx] == B["prov_f"].to_numpy()[b_idx],
]).astype(int)
fields = ["family", "middle", "given", "year", "month", "day", "province"]
K = len(fields)
is_match = np.array([(a, b) in true_pairs for a, b in cand])

# EM on the distinct comparison patterns (at most 2^7 = 128 of them).
patterns, inverse, counts = np.unique(G, axis=0, return_inverse=True, return_counts=True)
inverse = inverse.ravel()
# Start u at the overall agreement rate (nearly every candidate is a non-match)
# and m at a high common value.
p, m, u = 0.01, np.full(K, 0.9), G.mean(axis=0)
for _ in range(1000):
    lm = np.prod(m ** patterns * (1 - m) ** (1 - patterns), axis=1)
    lu = np.prod(u ** patterns * (1 - u) ** (1 - patterns), axis=1)
    g = p * lm / (p * lm + (1 - p) * lu)
    p_new = (counts * g).sum() / counts.sum()
    # M-step with a pseudo-count of one agreement and one disagreement per class,
    # which keeps m and u off the boundary so that no weight becomes infinite.
    m_new = ((counts * g) @ patterns + 1) / ((counts * g).sum() + 2)
    u_new = ((counts * (1 - g)) @ patterns + 1) / ((counts * (1 - g)).sum() + 2)
    converged = abs(p_new - p) < 1e-12 and np.allclose(m_new, m) and np.allclose(u_new, u)
    p, m, u = p_new, m_new, u_new
```

### Choosing thresholds and evaluating

A linkage is evaluated on pairs, with precision and recall defined relative to the true matches in the *full* comparison space, not only the candidates, so that blocking losses count against recall:
$$
\text{precision} = \frac{|\hat{M} \cap M|}{|\hat{M}|}, \qquad \text{recall} = \frac{|\hat{M} \cap M|}{|M|}, \qquad F_1 = \frac{2 \cdot \text{precision} \cdot \text{recall}}{\text{precision} + \text{recall}} .
$$
Accuracy is useless here, because declaring every pair a non-match is almost perfectly accurate.

```{python}
#| label: code-1204-thresholds
rows = []
n_true = len(true_pairs)
for T in [-4, 0, 4, 8, 12, 16]:
    pred = W > T
    tp = (pred & is_match).sum()
    prec = tp / max(pred.sum(), 1)
    rec = tp / n_true
    rows.append({"threshold_bits": T, "declared_matches": int(pred.sum()),
                 "precision": prec, "recall": rec,
                 "F1": 2 * prec * rec / max(prec + rec, 1e-12)})
print(pd.DataFrame(rows).set_index("threshold_bits").round(4))

review = (post > 0.05) & (post < 0.95)
print(f"\npairs in the clerical review band (0.05 < posterior < 0.95): {review.sum()}")
print(f"share of those that are true matches: {is_match[review].mean():.3f}")
```

Raising the threshold trades recall for precision in the familiar way. Recall can never exceed the pairs completeness of the blocking step. The posterior probability from EM gives a natural review band: pairs whose posterior sits between the extremes are few, and they are genuinely ambiguous, which is where a human reviewer or an expensive model adds the most value per decision.

## Beyond the Classical Pipeline

The modern stack keeps the same skeleton (normalize, block, compare, decide) and upgrades individual stages. Deep entity matchers such as Ditto serialize each record into text and fine-tune a pretrained transformer as a cross-encoder over record pairs, with large gains on dirty and textual records (Li et al. 2020). Since 2023, generative LLMs have been used as zero-shot or few-shot matchers that read two serialized records and answer whether they match, and published comparisons show they can rival fine-tuned matchers on unseen entity types, at a much higher cost per pair (Peeters et al. 2025). Because cost per pair is the binding constraint, these models belong at the end of the pipeline: lexical or embedding blocking reduces the space, Fellegi-Sunter or a small classifier settles the clear cases, and the LLM or a human reviews the narrow ambiguous band.

## Pitfalls and When to Use What

**Normalize Unicode before anything else.** Mixed NFC and NFD text corrupts tokens, hashes, and joins silently. Normalize to NFC at ingestion. Decide separately, per task, whether to fold diacritics, and when in doubt index both forms.

**Do not fold diacritics for semantic tasks.** Folding is a recall tool for names and search. For meaning, it merges distinct Vietnamese words and hurts any downstream model trained on accented text.

**Treat syllable tokenization as a known approximation.** Whitespace splits Vietnamese into syllables. Use a word segmenter, syllable bigrams, or character n-grams, and feed word-segmented text to models such as PhoBERT that expect it.

**Thresholds are model specific.** A cosine of 0.8 means different things for TF-IDF, for one embedding model, and for another. Calibrate thresholds on labeled pairs from your own data, and recalibrate when you change the model.

**Blocking caps recall.** Measure pairs completeness on a labeled sample before tuning the matcher. Use a union of keys on independent fields and avoid keys whose values are highly concentrated, such as Vietnamese family names.

**The conditional independence assumption is wrong but useful.** Fields such as province and phone area code are correlated, which makes Fellegi-Sunter overconfident. The ranking of pairs usually survives, but posterior probabilities should be recalibrated on labeled data before they are reported as probabilities.

**Pairwise decisions must be reconciled.** If $a$ matches $b$ and $b$ matches $c$, but $a$ does not match $c$, the pairwise output is inconsistent. Resolve it with a one-to-one assignment when each file has unique entities, or with clustering of the match graph for deduplication, and evaluate at the cluster level as well as the pair level.

**Pick the cheapest method that works.** For short names, normalized character n-gram TF-IDF is fast, transparent, and hard to beat. For sentences and cross-lingual text, use a fine-tuned bi-encoder for retrieval and a cross-encoder or LLM to rerank. For multi-field records, use blocking plus Fellegi-Sunter or a supervised classifier, and spend expensive models only on the ambiguous band.
